# IoT: устройства, сообщения, топики, подключение

В MVP все устройства программные (симулятор `simulator/sim.py`, `source_mode = simulator`). Реальное оборудование подключается через шлюз-адаптер, который публикует сообщения того же контракта с `source_mode = real`. Телеметрия используется для наблюдения и планирования; система ничем не управляет.

## Типы источников

| Тип (`kind`) | Событие | Что позволяет установить | Чего недостаточно по одному измерению |
|---|---|---|---|
| `track_circuit` | `occupancy` | занятость участка пути в момент измерения | свободен ли путь сейчас, если данные устарели; какой поезд стоит |
| `rfid_reader` | `rfid_read` | номера вагонов, прошедших контрольную точку, направление | отсутствие нового чтения не подтверждает отсутствие вагона |
| `loco_gps` | `position` | координаты (м) и скорость (км/ч) маневрового локомотива | потеря координат не означает освобождения пути |
| `switch_sensor` | `switch_position` | наблюдаемое положение стрелки (normal/reverse/unknown) | замкнут ли маршрут; система стрелками не управляет |
| `cargo_equipment` | `equipment_state` | работа/простой/отказ механизма, нагрузка (т) | причину и длительность отказа |
| `repair_diag` | `diagnostics` | температура буксы (°C), толщина гребня (мм), вердикт по вагону | окончательное техническое заключение |
| любой | `heartbeat` | связь и техсостояние: батарея %, сигнал дБм, время работы с | достоверность последнего измерения (это отдельный признак) |

Диагностика с вердиктом `faulty` регистрирует инцидент «Неисправный вагон» один раз: повторная доставка того же `event_id` отсекается. Отказ оборудования по телеметрии создаёт инцидент «Отказ ресурса», который снимается при возврате в работу.

## Топики MQTT

`station/{station_id}/{device_kind}/{device_id}`, QoS 1. Занятость и положение стрелок публикуются как retained. Сервис приёма подписан на `station/#` с постоянной сессией (`clean_session=False`, client_id `digital-station-ingest`), поэтому после перезапуска backend брокер доставит накопленное.

## Контракт сообщения (schema_version 1.0)

```json
{"schema_version": "1.0", "event_id": "c0f1…", "device_id": "ALM-TC-3", "station_id": "ALM",
 "object_id": "ALM-T3", "event_type": "occupancy", "observed_at": "2026-10-01T07:12:03.120Z",
 "sequence_number": 1842, "boot_id": "boot-1a2b3c4d", "payload": {"occupied": true},
 "quality": "good", "source_mode": "simulator"}
```

| Поле | Правило |
|---|---|
| schema_version | поддерживается `1.0`; иначе `UNKNOWN_SCHEMA` |
| event_id | уникален в пределах устройства; повтор не выполняет действия повторно |
| device_id, station_id, object_id | должны совпадать с реестром и топиком |
| event_type | один из типов выше и разрешён устройству |
| observed_at | ISO 8601 с часовым поясом (реальное время устройства) |
| received_at | ставит сервер |
| sequence_number, boot_id | порядок в рамках сеанса; смена `boot_id` — перезапуск, счётчик начинается заново |
| payload | значения с единицами `{"value": …, "unit": "…"}` |
| quality | good / uncertain / bad |
| source_mode | simulator / real |

Измерения относятся к модельному миру симуляции, а связь и устаревание оцениваются в реальном времени.

## Единицы и диапазоны

| Величина | Базовая единица | Допустимые единицы | Диапазон |
|---|---|---|---|
| speed | км/ч | km/h, m/s (×3,6) | 0–120 |
| x, y | м | m | −1000…3000 / −500…1500 |
| load | т | t, kg (÷1000) | 0–80 |
| axle_temp | °C | °C | −50…200 |
| flange | мм | mm | 0–60 |
| battery | % | % | 0–100 |
| rssi | дБм | dBm | −130…0 |
| uptime | с | s | ≥ 0 |

## Реестр устройств (`devices`)

Тип, станция, связанный объект, разрешённые типы сообщений, период передачи, порог устаревания, статус, режим источника, последнее соединение и heartbeat, последний `sequence_number` и `boot_id`, техсостояние. Конфигурация `large` содержит: 14 рельсовых цепей (порог 8 с), 22 датчика стрелок (20 с), 2 RFID (30 с), 2 ГНСС-трекера (6 с), 2 контроллера механизмов (20 с) и 1 диагностический комплекс ПТО (30 с). Порог по типу меняется в «Настройках».

## Проверки при приёме (`app/iot/ingest.py`)

Порядок проверок и коды отклонения (запись в `telemetry_rejects`, к состоянию не применяется):

| Код | Причина |
|---|---|
| BAD_JSON | не JSON |
| BAD_STRUCTURE | нет обязательных полей / неверные типы |
| UNKNOWN_SCHEMA, UNKNOWN_EVENT_TYPE | неизвестная версия схемы / тип |
| TOPIC_MISMATCH | топик не соответствует станции и устройству |
| UNKNOWN_DEVICE, DEVICE_DISABLED | нет в реестре / отключено |
| WRONG_STATION, OBJECT_MISMATCH, EVENT_NOT_ALLOWED | чужая станция / объект не связан / тип не разрешён |
| BAD_UNIT, OUT_OF_RANGE, BAD_PAYLOAD, BAD_TIME | единица, диапазон, содержимое, время |
| TIME_IN_FUTURE | время измерения опережает приём более чем на 5 с |
| TOO_OLD | измерение старше 24 ч |
| QUEUE_OVERFLOW | очередь приёма переполнена (защита от перегрузки) |

Принятые сообщения получают отметку `disposition`:
- **applied** — применено;
- **late** — пришло не по порядку или из прежнего сеанса; сохраняется в истории и не заменяет более новое наблюдение;
- **stale** — устарело (в том числе retained-сообщение старше порога); сохраняется, но не «освежает» данные.

Повторы (тот же device_id + event_id) отсекаются LRU-кэшем и уникальным индексом БД.

## Очередь и перегрузка (`app/iot/runtime.py`)

Значимые изменения (занятость, стрелки, RFID, диагностика) идут вне очереди частых координат. Координаты объединяются: на устройство хранится только последняя. Значимая очередь ограничена (`INGEST_QUEUE_MAX`, 20 000); при переполнении новое сообщение отклоняется с записью причины. Обработка идёт пакетами до 500 сообщений в одной транзакции.

## Отправитель (симулятор)

Ограниченный буфер — 2000 сообщений на время потери связи с брокером, досылка после переподключения. Также симулятор отвечает за heartbeat и счётчик `sequence_number` в рамках `boot_id`. По сценарию он моделирует неисправности: `silent` (молчание), перезапуск (новый `boot_id`), `stuck_free`, `duplicate`, `out_of_order`, `wrong_unit`.

## Безопасность

- Анонимный доступ к брокеру запрещён. У сервиса приёма и у симулятора разные учётные записи, файл паролей создаётся при старте контейнера из переменных окружения (`mosquitto/entrypoint.sh`).
- ACL (`mosquitto/acl`): `ingest` только читает `station/#`, `simulator` только пишет `station/#`.
- Для стенда с внешними подключениями в `mosquitto.conf` подготовлен закомментированный TLS-слушатель 8883 (сертификаты монтируются отдельно).
- Канал эталонного мира `/api/v1/sim/world` защищён отдельным токеном `SIM_WORLD_TOKEN`.
- Браузер получает данные только через backend.

## Подключение реального устройства

1. Зарегистрировать устройство в `devices`: `source_mode = real`, объект, разрешённые события, период, порог.
2. Выдать шлюзу отдельную учётную запись MQTT с правом записи в нужные топики.
3. Публиковать сообщения контракта 1.0 в `station/{station}/{kind}/{device_id}`.
