# ADR-0006. Запрет двойного бронирования ограничением-исключением БД

**Статус:** принято.

## Контекст
Две одновременно поступившие заявки не должны получить один ресурс, а конфликтную заявку нельзя подтвердить даже прямым API-запросом. Проверки только в коде приложения уязвимы к гонкам между транзакциями.

## Варианты
1. Проверка в приложении + `SELECT … FOR UPDATE` строк.
2. Сериализуемые транзакции.
3. Advisory lock станции на транзакцию проверки и резервирования + ограничение-исключение PostgreSQL как последний рубеж.

## Решение
Вариант 3:

```sql
EXCLUDE USING gist (resource_key WITH =, tstzrange(start_at, end_at, '[)') WITH &&)
WHERE (status = 'confirmed')
```

Для ограничения нужно расширение btree_gist. Подтверждение и применение плана берут `pg_advisory_xact_lock(hashtext('station:<id>'))` и заново проверяют состояние внутри блокировки. Нарушение ограничения переводится в ответ `409 RESOURCE_ALREADY_RESERVED`.

## Последствия
- Двойное бронирование невозможно ни при каком порядке транзакций; это подтверждает тест параллельного подтверждения.
- Порядок замены резервов важен: при переносе нескольких поездов сначала освобождаются все их резервы, затем создаются новые.
- Начальное заполнение проходит через то же ограничение, что дополнительно проверяет корректность генератора расписания.
