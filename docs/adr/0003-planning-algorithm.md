# ADR-0003. Алгоритм проверки и планирования

**Статус:** принято.

## Контекст
Нужны объяснимые отказы с точными причинами, быстрый пересчёт после сбоя (≤ 5 с), честные статусы оптимальности и гарантия, что жёсткие ограничения не нарушаются ради цели.

## Варианты
1. Только эвристика (жадное размещение).
2. Только MILP/CP-решатель для всего, включая проверку заявки.
3. Детерминированные правила для проверки + CP-SAT для перепланирования + эвристика как запасной вариант + независимый валидатор.

## Решение
Вариант 3.
- **Проверка заявки** — детерминированный earliest-fit с перебором путей по принципу best-fit. Он объясняет причину по каждому пути и ищет ближайшее окно с шагом 5 мин.
- **Перепланирование** — OR-Tools CP-SAT: интервальные переменные, NoOverlap по путям, стрелкам и ресурсам, выбор путей, ресурсов и маршрутов. Лимит 4 с, цель — минимизация взвешенной задержки и штрафов за изменение согласованных операций.
- **Валидатор** — результат решателя проверяется книгой интервалов; непроверенный план не предлагается.
- **Эвристика** запускается, если решатель не дал допустимого плана; её результат помечается отдельным статусом.

## Последствия
- Одно правило пересечений (`IntervalBook`, `reservation_specs`) используется в проверке, планировании, исполнении и подкреплено БД.
- Статусы различают «оптимальность доказана», «найден допустимый план», «не найден за отведённое время», «доказано отсутствие решения», «эвристика», «частичный план».
- Правила движка и планировщика должны совпадать, иначе решатель доказывает неразрешимость. Пример — технологический запас после освобождения пути: расхождение было обнаружено на живом стенде и устранено, теперь движок соблюдает тот же запас. Пересечение двух уже начатых операций рассматривается как факт исполнения, а не как нарушение.
