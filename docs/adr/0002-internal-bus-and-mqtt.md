# ADR-0002. Mosquitto для телеметрии и внутренняя шина событий

**Статус:** принято.

## Контекст
Презентация предусматривает сервисы приёма и шину Kafka/RabbitMQ либо её имитацию. Нужно принимать телеметрию от устройств (в MVP — от симулятора), не терять её при кратковременных сбоях, отделить устройства от браузера и связать модули backend событиями.

## Варианты
1. Kafka или RabbitMQ как общая шина для телеметрии и доменных событий.
2. MQTT-брокер (Mosquitto) для устройств + внутренняя in-process шина для доменных событий.
3. Устройства пишут напрямую в HTTP API.

## Решение
Вариант 2.
- **Mosquitto** — стандартный протокол IoT: QoS 1, retained-сообщения, постоянные сессии, ACL на топики, лёгкий (≈ 5 МБ памяти).
- **Внутренняя шина** (`app/core/bus.py`) публикует события только после фиксации транзакции (`after_commit`) и отбрасывает их при откате.
- **Браузер** получает данные только через WebSocket backend.

## Последствия
- Один брокер вместо двух; Kafka/RabbitMQ не добавлены без потребности.
- Повторная доставка MQTT (QoS 1) обрабатывается дедупликацией по `event_id`. Постоянная сессия (`clean_session=False`) позволяет получить накопленное после перезапуска backend.
- Внутренняя шина не переживает перезапуск процесса. Это допустимо: состояние восстанавливается из БД, клиенты получают полный снимок. Для нескольких процессов шину нужно заменить на `LISTEN/NOTIFY` PostgreSQL или брокер.
