Требование ≤ 5 с **выполнено** с запасом. Лимит решателя — 3,5 с. Если оптимальность за это время не доказана, возвращается лучший допустимый план со статусом «Найден допустимый план».

Начальный план рабочих сценариев оптимизируется при загрузке (см. [planning.md](planning.md)). Поэтому пересчёт после инцидента меняет только затронутые операции: при закрытии пути — 6 операций у 3 поездов, а не десятки.

### Поток телеметрии повышенной интенсивности (300 сообщений/с поверх фона, окно 15 с)

Метрики сбрасываются перед окном нагрузки (`POST /api/v1/metrics/reset`).

| Этап | n | p50, мс | p95, мс | max, мс |
|---|---|---|---|---|
| Передача: измерение на устройстве → приём backend | 4834 | 32,1 | 69,8 | 88,1 |
| Проверка и сохранение пакета телеметрии | 116 | 22,5 | 105,4 | 245,4 |
| Обновление модели станции после события | 54 | 189,3 | 360,3 | 497,8 |
| Сборка состояния станции | 81 | 33,3 | 97,0 | 129,8 |
| **Событие в backend → дельта получена WebSocket-клиентом** | 59 | **191,4** | **365,2** | **503,1** |

Применено 4834 сообщения. Очередь после теста пуста, потерь при переполнении нет.

**Отображение в браузере.** Отдельный прогон с подключённой вкладкой Chrome, окно 15 с, 750 обновлений. Время от получения дельты до обновления DOM: p50 22,9 мс, p95 35,4 мс, max 58,3 мс.

Вкладка была в фоне, поэтому замер шёл до обновления DOM (через `MessageChannel`), без кадра отрисовки. Для активной вкладки клиент меряет время до кадра через двойной `requestAnimationFrame`.

**Требование «видимое обновление < 500 мс после события в backend»:** доставка p95 365 мс + отрисовка p95 35 мс ≈ 400 мс — выполнено по p95. Максимум доставки 503 мс — на границе требования. Причина пиков — см. ниже.

### Известные пики и их причина

- **Пики до ~0,5 с на «обновлении модели» под нагрузкой.** Они совпадают с автоматическим пересчётом плана: построение модели CP-SAT на Python занимает GIL процесса. Меры уже приняты: пересчёт не чаще раза в 10 с, объединение событий, расчёт без блокировок БД. Следующий шаг (в бэклоге) — вынести планировщик в отдельный процесс.
- **Сброс сценария** с оптимизацией начального плана при первом запуске занимает ~25 с. На это время обновления состояния приостанавливаются; повторные сбросы того же сценария идут из кэша, ~0,5 с.
- **Расчёт плана в общей метрике «Время ответа API».** Запрос `POST /plans/compute` синхронно ждёт решения, до 3,5 с. Остальные запросы — p95 ≈ 120 мс.

## Как повторить

```bash
docker compose up -d --build
docker compose run --rm --no-deps -v ./tools:/tools simulator \
  sh -c "pip install -q websockets==13.1; python /tools/bench.py"
```

Параметры нагрузки: `BENCH_RATE` (по умолчанию 300 сообщений/с) и `BENCH_SECONDS` (15).

Бенч сбрасывает сценарии, поэтому в конце возвращает станцию в «Обычную работу».

## Найденные при замерах дефекты (исправлены)

1. **Перепланирование держало общую блокировку весь расчёт** — realtime замирал на 4 с. Теперь блокировка берётся только на чтение и сохранение.
2. **Движок не соблюдал технологический запас 5 мин после освобождения пути.** Планировщик видел пересечение двух уже начатых занятий и честно доказывал отсутствие решения. Правила движка и планировщика выровнены.
3. **Флаг «событие сценария выполнено» не сохранялся** (изменение вложенного JSON «на месте»), события срабатывали повторно. Исправлено.
4. **Открытая транзакция планировщика и `TRUNCATE` при сбросе сценария блокировали друг друга.** Такую межсессионную взаимоблокировку PostgreSQL не распознаёт. Теперь транзакции закрываются до расчёта, сброс выполняется под общей блокировкой. Стресс-тест: 8 сбросов подряд во время перепланирования, каждый за 0,3–0,6 с.
5. **Модельное время шло медленнее заданной скорости.** Внеочередные сборки состояния по телеметрии «съедали» прошедшее время. Найдено сквозным прогоном `tools/demo_e2e.py`: инцидент сценария не наступал вовремя.
6. **Начальный жадный план содержал устранимые задержки.** Из-за этого любой пересчёт менял десятки операций. Теперь начальный план оптимизируется детерминированно, с кэшем.
7. **Валидатор не проверял операции, оставленные эвристикой без изменений.** Их старые резервы сталкивались в БД с новыми. Теперь план проверяется целиком, а эвристика бронирует неразмещённые поезда заранее и не блокирует поезд его собственными резервами.
