# Архитектура

## Компоненты

| Сервис (Compose) | Технологии | Назначение |
|---|---|---|
| `db` | PostgreSQL 16 + btree_gist | Источник истины: модель станции, резервы, телеметрия, история, аудит; база `station_test` для интеграционных тестов |
| `mqtt` | Eclipse Mosquitto 2.0 | Приём телеметрии; анонимный доступ запрещён, ACL на топики, пароли генерируются из переменных окружения при старте |
| `backend` | Python 3.12, FastAPI, SQLAlchemy 2, Alembic, OR-Tools CP-SAT, paho-mqtt, ReportLab | API, WebSocket, движок симуляции, приём IoT, проверка ограничений, планировщик, помощник, отчёты |
| `simulator` | Python, paho-mqtt, httpx | Программные IoT-устройства (`source_mode = simulator`) |
| `frontend` | React 18, TypeScript, Vite, React Three Fiber, zustand, nginx | Интерфейс; nginx проксирует `/api`, `/ws`, `/docs` на backend |

### IoT-конвейер
Симулятор раз в секунду читает `/api/v1/sim/world` (защищён `X-Sim-Token`) и публикует показания. Сервис приёма проверяет сообщение (см. [iot.md](iot.md)), сохраняет его в `telemetry_events` или `telemetry_rejects`, обновляет `observations` и публикует `telemetry_applied`. Hub пересобирает состояние, а монитор качества данных при смене категории пути («актуально» ↔ «неизвестно») увеличивает версию состояния. Это запускает детектор конфликтов и перепланирование.

### Команды
Проверка заявки только читает данные. Подтверждение берёт `pg_advisory_xact_lock` станции, заново проверяет все ограничения на свежем состоянии и создаёт резервы. Ограничение-исключение БД не допускает пересечения резервов, а аудит пишется в той же транзакции.

### Realtime
См. [realtime.md](realtime.md).

## Внутренняя шина и MQTT

`app/core/bus.py` — in-process pub/sub. События, порождённые изменением БД, публикуются только после фиксации транзакции (хук `after_commit` сессии SQLAlchemy) и отбрасываются при откате. Подписчики: `Hub` (внеочередная сборка состояния) и `Replanner` (перерасчёт). Шина не гарантирует доставку между процессами: после перезапуска состояние восстанавливается из БД.

MQTT и WebSocket решают разные задачи. MQTT — вход телеметрии от устройств (QoS 1, постоянная сессия `clean_session=False`, retained-сообщения для занятости и стрелок). WebSocket — выход в браузер: снимки и дельты единого состояния. Браузер не подключается к брокеру, и учётные данные устройств ему не передаются.

## world_lock

`app/core/runtime_lock.py`. Сброс сценария выполняет `TRUNCATE` всех операционных таблиц. Если параллельно идут шаг движка, обработка пакета телеметрии или чтение модели перепланировщиком, PostgreSQL обнаруживает взаимоблокировку. Поэтому эти фоновые шаги берут общую блокировку на своё время, а сброс — на всё пересоздание данных (с повтором до 3 раз при deadlock). Перепланировщик держит блокировку только на чтение модели и закрывает транзакцию до запуска CP-SAT, чтобы не останавливать realtime на время решения.

## Масштабирование и ограничения

- Backend работает в одном процессе uvicorn (`--workers 1`): движок, приём телеметрии, hub и перепланировщик — потоки и асинхронные задачи одного процесса.
- Гарантии целостности (ограничение-исключение, advisory lock, ключи идемпотентности) реализованы в БД и сохраняются при нескольких процессах API. Движок, приём и hub при этом нужно выносить в отдельный процесс, а внутреннюю шину — заменить, например, на `LISTEN/NOTIFY` (см. ADR-0002).
- Демонстрационный объём: конфигурация `large` — 14 путей (главный I, парки А, Б, грузовой район, депо), 22 стрелки, 14 ресурсов, 43 устройства, 22–28 поездов за 10-часовое окно расписания.
