# Realtime: доставка, порядок, переподключение

Реализация — `backend/app/services/hub.py`, `backend/app/api/ws.py`, `frontend/src/lib/ws.ts`.

## Цикл обновления

1. Тик раз в 1 с реального времени (`SIM_TICK_SECONDS`): движок продвигает модельное время (× скорость) и выполняет переходы операций и события сценария.
2. Состояние станции собирается в единое представление (`view.py`): пути, поезда с позициями, операции в окне −3…+14 ч, ресурсы, инциденты, конфликты, рекомендации, заявки, проблемы датчиков, стрелки, индекс, план, KPI, окна обслуживания.
3. Строится дельта к предыдущему состоянию: для коллекций — `upsert` и `remove` по идентификатору, одиночные объекты заменяются целиком. Номер версии растёт.
4. Дельта рассылается клиентам и сохраняется в `state_deltas`; раз в 30 с сохраняется полный снимок в `state_snapshots`.

Внеочередная сборка запускается событием шины: применённая телеметрия или изменение планового состояния после commit. Чтобы не перегружать сервер при частых событиях, сборка выполняется не чаще чем раз в 100 мс. Частота потока в активном режиме — не ниже 1 Гц.

## Порядок и целостность

- Каждая дельта несёт `version` и `base = version − 1`. Клиент применяет её только при `base` = текущей версии. При пропуске он не показывает частичное состояние, а запрашивает полный снимок (`hello` с `last_version = −1`).
- Если клиент не успевает (очередь отправки > 200), сервер очищает его очередь и шлёт полный снимок.
- Событие шины публикуется только после фиксации транзакции, поэтому клиенты не видят незафиксированных изменений.

## Восстановление соединения

- Клиент переподключается с экспоненциальной задержкой 0,5 → 10 с со случайным разбросом; после трёх неудач показывается «Нет соединения» и кнопка «Переподключиться».
- При подключении клиент отправляет `hello` с последней применённой версией. Сервер досылает пропущенные дельты из кольцевого буфера (последние 600 дельт ≈ 10 мин) или полный снимок, если разрыв больше.
- После перезапуска backend номер версии продолжается от максимума в БД, буфер пуст — клиент получает снимок.
- Пока связи нет, интерфейс показывает последнее полученное состояние с явной пометкой о возможной неактуальности.
- Ping каждые 10 с без данных; по pong измеряется RTT.

## Метрики задержек (`GET /api/v1/metrics`)

Скользящее окно из 5000 значений на этап, отдаются p50/p95/max:

| Метрика | Этап |
|---|---|
| telemetry_transport_ms | измерение (observed_at) → приём backend |
| telemetry_persist_ms | проверка и сохранение пакета |
| model_update_ms | приём → сборка нового состояния |
| state_build_ms | сборка представления |
| event_to_ws_ms | событие в backend → отправка в WebSocket |
| ws_rtt_ms | RTT по ping/pong |
| client_render_ms | получение сообщения → два кадра `requestAnimationFrame` (отрисовка) |
| event_to_screen_ms | оценка: (event→ws на сервере) + RTT/2 + client_render |
| plan_compute_ms, check_ms, api_ms | планировщик, проверка заявки, ответ API |

### Методика клиентских замеров
Часы браузера и сервера могут расходиться, поэтому сквозная задержка складывается из измерений на каждой стороне по своим часам: серверный отрезок (сервер) + RTT/2 + отрисовка (клиент). Клиент отправляет выборки раз в 10 измерений. Браузер приостанавливает `requestAnimationFrame` и замедляет таймеры в фоновой вкладке, поэтому клиентские метрики достоверны только при видимой вкладке. Это учитывается в [performance.md](performance.md).
